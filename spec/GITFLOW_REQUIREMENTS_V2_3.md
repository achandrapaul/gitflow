# GitFlow — Unified Product, UX and Git Requirements (v2.3)

**Status:** Sole active normative requirements document. **Version:** 2.3. **Date:** 29 October 2026.

This file consolidates all approved v2.3 behavior and the still-required core Git semantics. It is the single source of truth; there are **no separate earlier-version requirements or override chains** in this handoff. Supporting tests are verification artifacts, not independent feature specifications. Do not invent new product features.

## Product, scope, and outcomes
- **Application:** `gitflow`, a terminal-native, keyboard-only Git application for macOS and Linux. No mouse or desktop GUI is necessary.
- **Product intent:** Lazygit-like quick interaction with IntelliJ-style history, cherry-picking, rebase and conflicts. A new GitFlow user should grasp the main inspect → stage → commit loop in minutes.
- **Startup:** First interactive frame targets **100 ms**, measured (cold/warm p50/p95 on documented hardware). Start directly in S01 Unified Changes Explorer, never a splash/dashboard/onboarding wizard. Load expensive history and data incrementally after the first frame.
- **Git behavior:** Use native Git semantics and real Git repository state as truth; UI navigation never mutates the index, worktree, refs or sequencer. Unapproved features are prohibited.
- **Required core:** unified changes/diffs/file-hunk-supported-line staging, single commit composer and review, amend, branch/upstream/main comparisons, create/switch/delete local branches, fetch/pull/push, read-only stash listing, paginated history, multi-commit cherry-pick, selective historic file application, visual interactive rebase, guided conflicts and paused operation recovery, context actions/help and explicit on-disk file deletion.
- **Safety:** No implicit fetch/rebase/force push/checkout/stash/discard/delete. Two narrowly approved user-authorized tracked-stash workflows exist: guarded branch-switch recovery (ST02), and dirty **whole-commit cherry-pick** recovery with post-success automatic restoration (ST03). Never create a stash without the user's explicit choice; restoration is automatic **only** for the stash created under that specific ST03 authorization. No automatic overwrite. Destructive actions require deliberate confirmation; Esc never aborts, skips, resets, discards Git work or continues sequencer operations.
- **Excluded features:** PR/hosting APIs, CI/issue tracker, general stash creation/apply/pop/drop/clear or stash-manager mutations (**only** ST02 branch-switch recovery and ST03 whole-commit cherry-pick recovery exceptions), new merge initiation planner, bisect, submodule manager, release/tag builder, reflog recovery center, theme editor, mouse features, AI commit generation, telemetry, account login, plugins, learned command suggestions and background daemon. Do not add features without approval.
- **Implementation language:** Go or Rust may be selected via a documented ADR considering 100 ms startup, terminal libraries, Git process handling, portability, tests and packaging. No implementation language is mandated.

## K01–K09, K29–K47 — Keyboard and action dispatch
- `Enter` opens/inspects the focused row; on conventional action-list menus it activates the highlighted entry. It never stages/commits/cherry-picks solely by opening a repository object. Exception: `Enter` in the explicit post-creation Switch? prompt chooses the labeled Switch action; ordinary S11 Enter remains inspection. No generic Enter choice exists in the `g` Git operation menu.
- `Space` toggles selection of the focused selectable object in its *current typed domain*, never mutating Git. In S01, the more specific selection contract below applies.
- `Esc` closes the top overlay, returns one UI level, or in S01 clears an explicit file selection as specified below. In S01 with no overlay and no selection, root Esc is a no-op. In S13 inspector, Esc returns to whole-commit mode retaining separately stored selections. It never aborts Git operations.
- `j/k` and arrows navigate; `h/l` or horizontal arrows expand/collapse hierarchical items where relevant; `Tab`/`Shift+Tab` cycle panels; `G` goes to the last loaded row; `Ctrl+D/U` scroll half a page; `gg` is **unbound**.
- `a` opens contextual actions and its approved second-key mnemonics only in matching contexts; `g` is the global action prefix available across normal non-text navigation. Neither prefix mutates Git by itself; `:` opens the palette; `/` searches/filters in scope; `?` opens scope-specific help. `q` returns from detail, and in root initiates explicit Quit without changing Git.
- S01 `1/2/3/4` choose All/Staged/Not staged/Mixed; S01 `s` stages, `u` unstages, `d` opens guarded Discard changes; `j/k` moves focus without selection mutation, `Space` toggles only focused file, `Shift+S` selects all changed/untracked files in every filter/closed folder, and `Shift+↑/↓` (when supported) or `Shift+J/K` changes a contiguous visible file selection range.
- In S07, `Shift+J/K` reorders rebase todo rows and `p/r/e/s/f/d` choose Pick/Reword/Edit/Squash/Fixup/Drop; `v` previews. In S06, `Shift+J/K` reorders the whole-commit queue and `p` previews. These are scoped bindings and do not conflict with S01.
- S08 `c` Continue, `s` Skip only when Git supports it, `A` request guarded Abort, `r` Refresh; S09 `1/2/3` choose supported conflict variants, `n/N` move among regions, `e` opens configured editor.
- Approved two-key mappings have one dispatch and one handler per action. `a v` (commit context) invokes one-time verified hook-bypass review; `a n` creates a local branch in branch context; `a m` starts Create from Main in branch context; `a u` sets upstream for the contextually selected local branch; `g h/b/n/s/u` act globally. `a e` is **unassigned** and must not execute any Git operation. Input/edit scope owns letters and must not trigger actions. Key precedence: focused text input/editor → top overlay → active planner → focused panel → global navigation. No consumed keystroke is dispatched twice.
- Each user action has one shared registry identifier, title, scope, target predicate, availability predicate with reason, review/confirmation rule, handler and post-action refresh policy. Shortcuts, contextual menus and palette must call the same implementation.
- Overlay-first `Esc` dismisses the overlay without clearing underlying checked selections. The next `Esc` in S01 clears all explicit file selections; with no selections/root it is a no-op. S13 `Esc` still restores S06 whole-commit mode and retained typed selections. Esc from a modified unexecuted plan may ask to discard **the UI plan only** with Cancel as safe default; it never discards Git changes.

## C01–C24, U01–U07 — Changes Explorer and learning contract
- **One file per path:** each changed/untracked repo-relative path appears once in All with distinct INDEX (HEAD→index) and WORKTREE (index→worktree) Git statuses. Unmerged, renamed, deleted, binary and untracked files are truthfully represented, not simulated as staged Booleans.
- **Filters:** All = any changed/untracked; Staged = every index-changed path **including Mixed**; Not staged = every path with unstaged changes **including Mixed** plus untracked; Mixed = paths with both index and worktree changes. A Mixed path occurs at most once per filter and appears in all four.
- **Diffs and stage:** S02 shows staged and unstaged diffs independently; selected file/hunk/supported line stages or unstages with safe native index manipulation. Invalid partial patches are blocked with reason. Binary staging is file-level only. Selection itself does not stage.
- **Focus and selection (C18/C20):** `j/k` (and unmodified arrow navigation) moves focus ONLY and never adds/removes selected files, regardless of any current multi-selection. A focused row is highlighted, not implicitly checked. When no explicit selected set exists it is the implicit single-file action target. `Space` toggles checked membership of ONLY the focused file. `Shift+J/K` (or Shift+up/down when terminal supports it) deliberately extends/contracts a contiguous range of visible FILE rows from a stable anchor; exclude folder headers. Independently Space-checked members survive range contraction; Space toggles take effect on the focused member even within a range. `Shift+S` explicitly selects all changed/untracked files including filter-hidden/collapsed ones. `Esc` in S01 clears every checked member and range anchor, preserving focus, scroll and Git state; if an overlay is open the FIRST Esc closes the overlay and the NEXT Esc clears selections. Do not implement implicit batch auto-join, sticky deselection exclusions or navigation-driven mutation.
- **Action targeting:** when one or more explicitly checked members exist, mutations target **ALL** those members even when current filters or collapsed folders hide some; before execution show full selected count and hidden target count (e.g. `3 selected · 2 hidden`), never silently exclude hidden selections. In the existing action review, enumerate **all** repo-relative target paths, visibly distinguish hidden paths, state the action for each, and show eligibility/blockers; do not create a mandatory modal for ordinary eligible direct stage/unstage. Ineligible members must be reported truthfully without silently replacing the target with the focused file. The mutation targets only selected members, not a focused-but-unchecked row; with no explicit checked members and no pending selection gesture, use the focused file as the sole default action target. An explicit empty/invalid range or stale selection gesture must not silently retarget—show the blocker. Always show checked/hidden counts and exact intended mutation scope; reviewed batch actions must never hide the full path list or silently omit hidden checked rows. Preserve stable file identities across filters/inspection; reconcile after real Git changes and restore focus/scroll or nearest surviving row.
- **Flat/Folder:** `v` toggles immediately between Flat (first-run default) and By folder. Persist a **global per-user preference** across restarts/repositories using an atomic config write; never change mode automatically. Folder nodes group the same paths, may expand/collapse, and never act as changed files or implicitly select/stage/delete descendants. If preference saving fails, show truthful diagnostic.
- **Delete file from disk (C14):** only S01 `a` → Delete file from disk (or matching palette action), for exactly one eligible selected file or focused file when no batch exists. Preview exact repo-relative path, tracked/untracked/staged state and irreversible loss; require explicit confirmation. Delete only that on-disk file/symlink without following symlinks, never a folder, submodule, conflicted file, stale target or multi-file batch. Never auto-stage, unstage, restore or reset; re-read native status. Keep `d` **Discard changes** distinct and guarded.
- **Commit (C10/C22/C23):** one inline subject/body draft; `c` focuses the existing composer, S03 reviews the same draft against the **current staged index**. No staged changes → disabled with reason. The user explicitly commits after review; if the index changed, invalidate stale review. Normal Commit honors Git hooks/signing. Record the reviewed index tree identity and message before execution; after Git succeeds inspect the actual new HEAD tree/message (and confirm the intended commit was created) and disclose any hook-induced difference from review with a way to inspect the actual commit. If a hook fails after changing index/message, retain draft and actual Git state, invalidate stale review and require re-review; never auto-reset or falsely claim index unchanged. **C23:** provide a separate contextual **Commit without verification hooks** action using native `git commit --no-verify`, guarded by one-time explicit warning/confirmation and the same GitFlow preflight/review. Only Git-supported `pre-commit` and `commit-msg` bypass is promised; do not claim all hooks are skipped. Do not persist bypass, auto-retry, disable signing, or bypass GitFlow safety checks. Approved `a v` in the commit context is the sole new hook-bypass mnemonic; it enters the same explicit reviewed one-time action, not an instant commit. Preserve draft on failure; clear only after verified success. Amend uses `a` and warns of published-history rewrite; never auto-force-push.
- **Learnability:** concise relevant shortcut footer, obvious active focus and selection marks, one-screen core commit workflow, no onboarding wizard. Five first-time GitFlow users familiar with Git: target at least 4 reaching commit review (inspect+stage) within five minutes; measure rather than claim completion without evidence.

## B01–B11, H01–H08 — Branches and History
- The S01 header and S11 branch inspector show current branch (or detached HEAD), current HEAD OID, configured tracking upstream or “No upstream”, locally derived ahead/behind counts, independent comparison against `origin/main` or local `main`, and remote-tracking freshness/unknown. Do not conflate upstream with main or invent fresh remote data.
- `g b` globally opens S11's local/remote branch list; S01 `b` remains an existing alias. Search and `Enter` inspection never switch. S11 `s` deliberately requests a switch to the focused local branch after native dirty-state/sequencer checks; a blocked dirty switch offers the guarded ST02 recovery or leaves the original branch untouched. Remote-tracking refs never silently become checked-out local branches.
- **B08 — Local branch creation:** `g n` opens Create Branch using current HEAD as the default start point; `a n` exists only in a branch context (S11 focused branch/ref or S01 branch header) and opens the same creation review using that explicitly shown starting ref. The user chooses/confirms the new local branch name and start point. On creation, create the local branch only: **no automatic checkout, no push, and no speculative upstream**, even if `origin/<branch>` has not been fetched or created. After success show `Created <new> · Still on <current>` and the focused `Switch to <new>?` prompt; `s`/`Enter` deliberately requests switch, `Esc` dismisses without deleting the branch or changing checkout. A normal S11 Enter still inspects. Revalidate names, refs, target existence and repository state; on invalid state show a blocker, never silently switch or overwrite a ref.
- **B10 — Create Branch from Main (`a m`):** Available in S01 branch-header and S11 branch context, independent of which local branch/ref is focused. This action always uses the **local `main`** branch as its source; it does not act on a selected source branch and does not change checkout during branch creation. Ask for and validate the new branch name, display the actual starting ref/OID, and compare local `main` to cached `origin/main` without implying the remote is live. If known behind, offer `p` **Update main & create**, `c` **Create directly from local main**, and `Esc` **Cancel** in the explicit choice prompt. `p` explicitly authorizes obtaining the remote tip and fast-forwarding **local `main`** (the user's intended pull-equivalent), then creates from that updated local `main`. When another branch is checked out, use native Git fetch with an explicit `main:refs/heads/main` non-forced fast-forward-only local-main ref update instead of pulling into the currently checked-out feature branch; when `main` itself is current, use native `git pull --ff-only origin main` with working-tree safety checks. Do not merge or rebase, change the current checkout, stash, discard or overwrite current tracked/untracked changes as part of this update. `c` uses unchanged local `main` without any network access or update. For missing `main`, missing origin/remote ref, divergence, authentication/network failure, unsafe update or failed creation, show the specific result and offer direct creation only if local `main` exists; never claim a successful update. A successful update followed by failed branch creation must report that local `main` was updated and the new branch was not created; no false rollback. The normal B08 post-create Switch? prompt follows successful branch creation. If `main` is synchronized with cached `origin/main`, direct creation can proceed without a behind warning; do not claim fresh remote knowledge.
- **B11 — Explicit switch and guarded dirty recovery:** After **any** successful `g n`, `a n`, or `a m` branch creation, offer `s`/`Enter` to switch to that exact newly created branch and `Esc` to remain on the original branch. No checkout happens before the choice; closing the prompt never deletes a branch. Later S11 `s` switches the explicitly focused **local** branch; S11 `Enter` only inspects. If a requested switch fails or is safely detected to be blocked by dirty tracked changes, show actual affected paths and allow `s` **Stash and Switch** (ST02 review) or `Esc` **Stay and fix manually**. The branch switch must be revalidated after stash; if it remains blocked, preserve the stash, current checkout and truthful failure. For unmerged state, incompatible sequencer or untracked collision, explain the actual blocker rather than implying tracked stash will fix it. Never auto-apply/pop the stash after switching.
- **B09 — Upstream lifecycle:** `g u` opens explicit configuration for the currently checked-out local branch; `a u` in a branch context opens configuration for the selected local branch. Show local branch and actual remote/ref target for deliberate approval. If there is no upstream, `g P` must first review the proposed push destination `origin/<current-local-branch>` and indicate whether creating the remote ref is expected or remote state is unknown; if confirmed, use native `git push --set-upstream origin <local-branch>` so successful push establishes tracking. Never preconfigure a speculative upstream during creation, silently push, force-push, or claim tracking succeeded after a failed/uncertain push. If `origin` does not exist, the default first-push route is blocked with a specific reason. If upstream already exists, ordinary push respects it and must not silently replace it. Non-fast-forward rejection and native authentication still apply; re-read native tracking config and refs after the push. Explicit `g u`/`a u` must not implicitly fetch/push/checkout.

- `g h` opens S04 with bounded, incrementally paginated and virtualized commit graph/history (initial target: 100 commits; prefetch before bottom). Preserve full-OID selection, focus, filters, scroll and correct graph boundaries across loads. Search scope is clearly labeled as loaded-only or full repository.
- Source-branch selection for History/Cherry-pick is read-only: it changes displayed commits, **never** the checked-out HEAD or target branch. From S04 and every existing branch-specific commit listing, `g c` carries source-branch context and whole-commit/file selections into the same S06 explorer. `Enter` inspects a commit; `Space` selects a whole commit in the relevant commit list.
- Existing commit compare actions are available for exactly two selected commits. Interactive rebase starts from explicit base/range (History contextual Actions entry; a proposed `r i` direct shortcut is still deferred and is not bound), never from an arbitrary list misrepresented as a contiguous rebase range.

## ST01–ST03 — Read-only stash list and narrowly approved recovery workflows
- `g s` opens S16 displaying real `git stash list` entries in current-repository order (stash reference/identity, message, date and source branch only when Git provides reliable data). Opening, scrolling, filtering and closing S16 are read-only; never apply/pop/drop/clear/create a stash **from S16**. Show empty list and parse/read errors honestly, with no fabricated stash entries. Repository and selection context is restored on return. No implicit network operation or working-tree modification. General stash mutations remain out of scope, including contextual and palette actions; **only ST02 and ST03** authorize stash mutations inside their specific reviewed workflows.

### ST02 — Explicit Stash and Switch exception (B11 only)
- The approved **branch-switch** stash mutation is a one-time user-initiated **Stash and Switch** recovery when an explicit local-branch switch is blocked by tracked working-tree/index changes. In the blocker prompt `s` opens S10 action review (not immediate stashing); show current branch, requested target, exact tracked changes to be stashed and whether untracked files are excluded. Require the existing S10 explicit `c` confirmation, with `Esc` Cancel default. Execute native `git stash push` for tracked changes (no `-u`/`-a`) only after confirmation; confirm it succeeded before retrying the requested checkout. Never stash automatically merely because a switch was requested.
- Do not stash untracked paths; if a collision prevents switching, show the blocker and require manual handling. Never stash when unmerged entries/incompatible native operation make it unsafe. A failed stash means **no switch**; if stash succeeded but switch failed, keep the stash intact, show its real identity and current branch, and leave recovery manual. Never automatically restore/apply/pop/drop the stash, never discard other changes, and never promise that stash+switch is atomic. Existing S16 remains strictly read-only and receives no new stash commands.

### ST03 — Dirty whole-commit Cherry-pick: Stash, Execute, Restore
- This is a **whole-commit cherry-pick only** exception. A clean tracked index and worktree execute selected whole commits directly: **no stash creation, no stash apply/pop/drop and no restoration prompt**, including when noncolliding untracked files exist. Do not perform speculative stash operations. S13/S14 selective historical-file application **does not** use ST03; it continues to require clean tracked index/worktree at execution and creates no commit.
- When tracked staged and/or unstaged changes exist, keep S06 read-only inspection, selection, reordering and preview available. On deliberate **Cherry-pick selected commits** Execute, run preflight and display an explicit blocker with affected paths, selected commit count/order, target and **`s` Stash and Proceed / `Esc` Cancel execution**. `Esc` returns to the explorer with selections/changes intact; it does not abort Git. `s` is the deliberate authorization for the shown, scoped tracked-only stash and subsequent reviewed cherry-pick sequence. Never stash untracked paths (`-u`/`-a` prohibited), silently stash on inspection, or offer this as a remedy for an unmerged index, incompatible sequencer, untracked path collision or unsupported mutation. Revalidate native state and selected OIDs before stashing/performing Git mutations.
- After `s`, create **one real tracked-only stash** including index and worktree changes, and capture its exact immutable commit OID and current stash identity (never assume `stash@{0}` will remain fixed). Verify stash success and a clean tracked preflight; **only then** execute selected whole-commit cherry-picks in their reviewed order with native Git. If stash creation fails, do not cherry-pick. If the queue fails, pauses for cherry-pick conflicts, or is skipped/aborted before full success, **do not restore yet**: retain the stash, report actual committed/pending steps and native recovery options; never undo successfully created commits merely because restoration is pending. If user continues and completes the whole cherry-pick queue, then restore; if user aborts the cherry-pick, retain the stash and report the outcome instead of silently applying it.
- **Only after all selected cherry-picks have successfully completed as actual commits**, with no active sequencer and with a revalidated clean tracked index/worktree, record a post-cherry-pick recovery baseline (HEAD full OID, index and tracked-worktree state, plus relevant untracked-path safeguards). Automatically attempt to apply **only the workflow-created stash** to the **same checked-out target** using native stash semantics, preserving prior staged state where supported (e.g. `git stash apply --index <recorded-stash-OID>`). Do not use unverified `stash pop` or restore a different stash; retain the recovery stash until restoration success is verified. If the tracked state is unexpectedly dirty or repository/HEAD changes in the interim, stop and preserve the stash rather than overwrite anything.
- On verified **conflict-free restoration**, report that cherry-pick commits succeeded and original tracked changes/staged state were restored; remove **only** the verified workflow-created stash using its current validated ref when safe. If removal fails, report restore success **and** that the stash still exists, with its real identity. A successful cherry-pick is never misreported as rolled back because stash restore or cleanup fails.
- If stash restoration partially applies and creates conflicts, display **`c` Continue unstash / `a` Abort unstash** in an explicit top overlay, including conflicted paths and confirmation that cherry-picked commits are already committed. `c` retains partial restoration, opens existing S09 guided conflict resolution where supported (otherwise manual editor), and preserves the original stash as a backup. Native Git has no `stash --continue`; this is **not** a paused cherry-pick/sequencer and must not invoke `git cherry-pick --continue`, create a commit or claim automatic resolution. Finalize restoration only after real conflict/index revalidation and explicit user completion; preserve the backup stash after manual conflict resolution unless a separately validated workflow cleanup can safely prove completion. `Esc` only dismisses/navigates, never discards files.
- `a` means **abort the attempted unstash only**, not `git cherry-pick --abort`. Require explicit confirmation of rollback impact; restore the recorded post-cherry-pick tracked/index baseline only if GitFlow can safely attribute all affected edits to its own attempted restoration and verify no external/intervening changes or untracked collateral. Keep completed cherry-picked commits and the original stash untouched. Git has **no native `stash --abort`**; never issue an unconditional `git reset --hard` or `git clean` that could erase unrelated work. If exact rollback cannot be proven safe, refuse automatic rollback, preserve actual state and stash, explain precise manual recovery. Revalidate final Git state before declaring rollback successful.
- If stash apply fails without modifying tracked state, report the failure and keep the stash; do not fabricate a conflict-resolution need. If it partially modifies state, offer the same explicit Continue/Abort restoration decision when safe. Existing S08 sequencer recovery remains distinct from S09 stash-restore conflict handling. No new screen, global binding or general stash management is approved by ST03.

## H04–H06, C21, UX-N05 — Cherry-pick Explorer and selective historical files
- S06 top header shows **source branch** (browsing only) and **target=current checked-out branch** (fixed/clearly labeled). Left side: paginated commits; right side: files and diff for the focused commit. Tab cycles branch/commit/file panes; `j/k` navigates; Enter on a commit enters S13 file-selection mode.
- **Entry and execution guards:** `g c` opens **read-only** S06 browsing/inspection and permits selection/preview even with staged or unstaged tracked modifications. No tracked cleanliness precondition at entry; incompatible active Git sequencers and unmerged entries remain hard blockers to new execution. At deliberate **whole-commit Execute**, clean tracked index/worktree → execute directly (no stash); dirty tracked index/worktree → offer ST03 `s` Stash and Proceed or Esc Cancel, subject to native preflight. At **selective-file Execute**, clean tracked index/worktree remains mandatory with **no** ST03 workaround. In either mode enforce unmerged/sequencer/untracked-collision guards immediately before mutation; show exact blocker/path. Never silently stash/discard/checkout or execute merely because a preview was opened.
- **Whole-commit mode (default):** Space selects full commit OIDs from left; selections can span viewed source branches; explicit ordered queue and `Shift+J/K` reorder; `p` previews; `a` exposes **Cherry-pick selected commits** Execute. ## Detailed native Git correctness
## Repository status authority
Use native Git commands, structured/parseable output, no screen-scraping. `git status --porcelain=v2 --branch -z` where applicable for working-tree and branch tracking. Account for rename, delete, conflict, binary, untracked, spaces/newlines in paths. Paths require NUL-safe processing. Git index/worktree can change independently.

## Changes filter truth table
Let I = index differs from HEAD; W = worktree differs from index; U = untracked. U is *not* a staged index diff.
| I | W | U | All | Staged | Not staged | Mixed |
|---|---|---|---|---|---|---|---|
| 0 | 0 | 0 | No | No | No | No |
| 1 | 0 | 0 | Yes | Yes | No | No |
| 0 | 1 | 0 | Yes | No | Yes | No |
| 1 | 1 | 0 | Yes | Yes | Yes | Yes |
| 0 | 0 | 1 | Yes | No | Yes | No |
This categorization includes deletes, renames, type changes and conflicts as statuses; unresolved conflicts get a clear special indicator. If an unresolved conflict makes I/W classification nontrivial, show conflict marker and surface it in All and the appropriate native state; do not misrepresent it as safely staged.

## File list and diffs
- All list: each changed/untracked path represented ONCE; INDEX and WORKTREE columns show Git XY status. Separate green staged and amber dirty indicators. Untracked `??` is visible.
- Staged diff: `HEAD → index` (`git diff --cached`, with safe pathspecs).
- Unstaged diff: `index → working tree` (`git diff`, with safe pathspecs). For untracked, show file as untracked content rather than fabricate tracked diff.
- Mixed inspector shows both staged and unstaged diffs with section headings. Commit review only summarizes the actual index, not the working tree.
- File stage/unstage use native Git index operations with pathspec-safe execution. Hunk/line partial staging must validate patch applicability and preserve unaffected working-tree and index content; use well-tested patch application methods. No arbitrary line selection guaranteed stageable. For binary files, file-level action only.
- Changes refresh after stage/unstage/commit/checkout/fetch-related ref updates. UI never infers stage status by toggling a Boolean.
- Discard is destructive, must preview scope and confirm. Never automatically use `git clean -fd` or discard untracked files in MVP.

## Branch intelligence
- Current branch, HEAD short object ID, configured tracking upstream, ahead/behind versus upstream, independently chosen comparison base.
- Default comparison base = `refs/remotes/origin/main` if available, otherwise `refs/heads/main` if available; if neither exists show `Base unavailable` and no ahead/behind count. Do NOT guess `master` or network-call automatically.
- Upstream is read via Git branch tracking configuration; if missing display `No upstream`, not 0/0.
- `git rev-list --left-right --count HEAD...<ref>` yields left-only (ahead) and right-only (behind) commit counts. Avoid relying on abbreviated hashes alone.
- Remote-tracking refs are locally cached; show “Local refs · last fetched unknown” unless trustworthy fetch time metadata exists. The app must not claim remote real-time freshness. Fetch is user-invoked.
- After switching branch, re-evaluate HEAD, upstream, base, and selected path state. If detached HEAD, show `DETACHED @ <hash>` and warning; do not invent branch label.
- A branch can be both ahead and behind. Do not equate diverged with broken; do not automatically rebase.
- Branch inspector (S11) shows remote, upstream, comparison base, counts, worktree status, and explicit fetch/pull/push and upstream configuration actions.

## Commit history pagination
- Read bounded chunks, initial target 100 commits; prefetch next before end; visible rows only + overscan.
- Pagination must maintain a stable traversal definition including options/filters/reference snapshot; refs changing can invalidate cursor and require a non-destructive refresh/notice.
- Git history is a graph, not a flat offset database. Cursor strategy must account for topo/order, merges and repeated commits; no missing/duplicate records from page boundaries. Test large DAG fixtures.
- Search/filter scope must be labeled (loaded-only versus full repo); do not misleadingly claim repo-wide search with loaded-only results.
- Preserve focus and selection across page loads, return visits and filters; hidden selection count surfaced.

## Git operation semantics
- Native operations: `git cherry-pick`, `git rebase -i`/sequencer, `git merge` as relevant to conflict dashboard; continue/skip/abort available per Git operation.
- Supported matrix:
  - Rebase: `git rebase --continue`, `--skip`, `--abort`.
  - Cherry-pick: `git cherry-pick --continue`, `--skip`, `--abort`.
  - Merge: `git merge --continue`, `git merge --abort`, **NO skip**.
- Detect state from repository metadata and Git plumbing as appropriate, not UI saved flags. Before each mutating action refresh status and validate preconditions.
- “Resume dashboard” = show S08, no Git execution; “Continue” = explicit Git mutation.
- Cherry-pick planner takes explicitly selected OIDs and order, executes sequentially, handles merge commits only with explicitly chosen mainline parent (otherwise block and explain).
- Interactive rebase requires explicit base/range and affected commits. No arbitrary noncontiguous set silently converted into a rebase range. Validate squash/fixup preceding commit and other todo constraints.
- Conflict resolver must display truthful branch/ref-or-commit identifiers and operation roles for each side; native ours/theirs/index-stage mapping stays internal and is specifically tested for rebase/cherry-pick reversals. For unsupported conflict types offer external editor/manually supported native resolution, not a misleading auto-resolve.
- Continue enabled only when known prerequisites satisfied. Git can still fail; always handle errors.
- Abort is never promised as universal undo, especially if unrelated worktree edits exist. Revalidate and confirm.

## Commit
- Composer displays subject/body editing (multiline) and currently staged paths/hunks only.
- Commit via native Git honoring configured hooks, signing and message rules by default; optional one-shot explicit `--no-verify` bypass only affects hooks Git supports skipping. Capture reviewed tree/message and compare actual successful commit tree/message; report differences, failed hook index modifications and real outcomes without undoing Git.
- Amend is separate action and warns when a commit may be published; no auto-force-push.
- Nothing staged → Commit unavailable with explanation; staged only with message → review → explicit execute.
- When Git status has unmerged index entries, block unsafe commit and route to conflict dashboard.

## Command process safety
- Execute binary+argv without shell expansion, repo cwd explicit.
- Never store or print credentials in logs; respect Git config and credential helper.
- Don't run parallel conflicting index/ref mutations within TUI; external process changes require revalidation.
- Errors show Git stderr and next safe action, not “success” based on anticipated output.
### Safe on-disk deletion specifics
- **Delete file from disk** is intentionally NOT **Discard changes**: it removes the specifically reviewed file/symlink in the working tree but never uses `git restore`/`reset`, automatically un-stages anything, or stages deletion. A tracked file then appears as worktree-deleted; an untracked file disappears from status. If the file was staged, its INDEX content stays staged, and the confirmation must explicitly warn that staged content could still be committed. User must separately stage a tracked deletion if desired.
- Confirmation shows path, whether tracked/untracked, current INDEX and WORKTREE state, and whether deletion loses modified/untracked content; default Cancel. **Never promise Git can recover untracked/deleted unstaged content.** Revalidate repo-relative path, type, Git status, and filesystem metadata immediately before unlink; if changed, stop and request a fresh review. Do not follow symlinks, delete directories, recursive trees, submodules/gitlinks, outside-repo targets, unmerged/conflicted entries, or multiple selected paths. Error/partial results must be truthful.
- The implementation may use a platform-safe single-file unlink primitive rather than `git rm`; `git rm` would stage the change and violate this action's defined semantics. Always re-read the index/worktree after operation; never fabricate status. Unsafe special objects are disabled with a reason.
